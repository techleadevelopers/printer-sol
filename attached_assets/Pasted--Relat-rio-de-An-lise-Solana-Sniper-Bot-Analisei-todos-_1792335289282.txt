 Relatório de Análise — Solana Sniper Bot
Analisei todos os 18 arquivos. A arquitetura é sólida em termos de segurança e engenharia defensiva, mas o bot tem problemas econômicos fatais com os defaults atuais que tornam lucro matematicamente impossível. Segue o diagnóstico.

✅ O que está bem feito (mantenha)
Área	Observação
Segurança de config	SIMULATION + ENABLE_LIVE_TRADING são mutuamente exclusivos, DBs separados obrigatórios, validação de esquema
Sessão admin	HMAC + subtle.ConstantTimeCompare, CORS com origins explícitos
Validação de TX	validatePreparedTransaction é conservador (fee payer, 1 signer, rejeita ALT)
Reconciliação	Persistência de trades antes de assinar + reconciliation_needed bloqueando novas compras
Anti double-buy	HasPurchaseForMint bloqueia reentry mesmo em falha — evita "averaging down" acidental
RPC manager	Health check + rotação por latência + rate-limit detection
Paper equity	Balanço carregado através de restart (simulationBalance + realized + openPnl)
Preço SOL/USD	Sem cache — falha fechada
🚨 Problemas CRÍTICOS (impedem lucro)
1. Economia dos defaults é negativa por construção
text
TRADE_USD         = 1      ($1 por trade)
MAX_PRIORITY_FEE  = .01    (≈ $1.50 a $3 por tx)
MAX_TRADE_SOL     = .05    (~$7.5)
MAX_EXPOSURE_SOL  = .2     (~$30 total)
TAKE_PROFIT       = 70%    (só vende se subir 70%)
STOP_LOSS (sim)   = 0      (nenhum stop em paper)
Cálculo rápido: trade de $1 com priority fee de $1.50 gasta 150% do capital só em taxa antes de qualquer slippage/pool fee. Você precisaria de +250% para empatar. O default garante prejuízo.

Ajuste mínimo aceitável:

text
TRADE_USD              ≥ 25       (para diluir fee)
MAX_PRIORITY_FEE_SOL   ≤ 0.001    (≈ 15–30 cents)
TAKE_PROFIT_GROSS_PCT  = 30–50    (não 70)
STOP_LOSS_PCT          = 15–25    (live E sim)
MAX_HOLD_SECONDS       = 120–300  (live)
2. Estratégia quase inexistente
strategy.Evaluate só valida: mint vazio + idade + duplicata + RugCheck. Não existe:

Checagem de dev holdings (quantos % do supply o criador segura)

Histórico do criador (quantos rugs anteriores)

Bundle detection (compra única no mesmo bloco)

Concentração de holders / sniper count

Liquidez inicial mínima

LP burn vs. locked

Freeze/mint authority ativa

RugCheck summary sozinho aprova >70% dos rugs reais em pump.fun. Precisa dos endpoints report completo + holders + insiders.

3. Saída é só TP fixo — sem trailing, sem ladder
positions.ExitReason só dispara em stop/take/max-hold. Nenhum:

Trailing stop (o que mais salva sniper de pump.fun — pumps revertem em segundos)

Ladder de saída (vender 50% em +30%, 50% em +60%)

Exit por degradação de momentum (volume cai, holders caem)

Sem trailing stop, você devolve todo lucro em pump-and-dump clássico.

4. Entry sem esperar o "first dip"
monitor.consume dispara BuyNewTokenUSD imediatamente na detecção. Clássico sniper de pump.fun:

Espera 2–8 segundos pelo primeiro retrace (5–25%)

Confirma que dev não vendeu no bloco 0

Confirma que não há bundle único

Entrar no topo do candle inicial é o pior timing matemático.

5. reserved map vaza em timeout/unknown
Em execution.confirm:

go
case <-ctx.Done():
    _ = e.db.UpdateTradeState(id, "unknown", sig, false)
    e.emit("risk_alert", ...)
    return  // ← NÃO chama e.release(r.Mint)
E também na path submitted != signature. Cada trade travado queima permanentemente uma entrada em reserved. Depois de ~N trades o bot fica permanentemente sem saldo livre até restart.

Correção: defer e.release(r.Mint) no início de confirm, mas só se o DB confirmar estado final. Ou liberar com base em state == "unknown" após reconciliação.

6. seen em monitor nunca é limpo
m.seen sync.Map cresce indefinidamente — em produção (milhares de mints/hora) estoura RAM em dias.

7. WebSocket /ws/events sem autenticação e CheckOrigin: true
go
var up = websocket.Upgrader{CheckOrigin: func(r *http.Request) bool { return true }}
Qualquer site pode abrir WS e ver todos os eventos (mints, trades, PnL). Não é RCE, mas é vazamento de edge — sua lista de tokens comprados é ouro para MEV bots front-running seu próximo exit.

Correção: exigir token HMAC na query string do WS ou no primeiro frame.

8. Token de sessão sem expiração
go
func (s *Server) sessionToken() string {
    mac := hmac.New(sha256.New, []byte(s.cfg.AdminPassword))
    _, _ = mac.Write([]byte("solana-sniper-admin-session-v1"))
    return hex.EncodeToString(mac.Sum(nil))
}
O token é estático para sempre até trocar senha. Vazou uma vez (log, screenshot, DevTools), o atacante controla o bot até você trocar ADMIN_PASSWORD. Adicionar timestamp no payload + janela de 1h.

9. cors (lowercase) é código morto
go
func cors(next http.Handler) http.Handler { ... }  // nunca chamado
New() usa corsPolicy. O cors ainda define Access-Control-Allow-Origin: "*" — se algum dia for ativado por engano, é CVE. Remova.

⚠️ Problemas MÉDIOS (afetam edge, não quebram)
10. RugCheck provavelmente tem bug de escala
go
if report.Score > 20 || report.LPLocked < 50 {
A API /report/summary do rugcheck.xyz retorna score_normalised na escala 0–1 (não 0–100) em versões atuais. Se for 0–1, > 20 nunca dispara — você está só validando LP lock.

Verificar manualmente com um mint conhecido ruim e confirmar a faixa do campo. Adicionar log do score em token_rejected para telemetria.

11. Confirm goroutine sobrevive ao shutdown
confirm usa context.Background(). Se o processo encerra no meio, goroutines ficam penduradas. Passar contexto raiz cancelável do main.

12. Submissão com maxRetries: 0 + skipPreflight: false
Isso maximiza latência (preflight redundante em pump.fun onde pré-flight quase sempre falha por conta do estado volátil). MaxSubmissionAttempts = 1 também é baixo demais para RPC público.

Sugestão:

skipPreflight: true + preflight próprio via simulateTransaction opcional

MaxSubmissionAttempts = 3 com backoff

maxRetries: 2 no RPC (mas só para "blockhash not found" transient)

13. Priority fee é fixo
MaxPriorityFeeSOL é um cap, mas priorityFee passado adiante é o mesmo todo trade. Dynamic priority fee (olhar getRecentPrioritizationFees e usar 75º percentil) é o que separa snipers que pegam o bloco certo dos que ficam 1 slot atrás.

14. takeProfit/stopLoss calculados sobre cost = 1 fictício
go
reason := positions.ExitReason(
    positions.Position{Mint: mint, CostSOL: 1, OpenedAt: openedAt},
    1+returnPct/100, true, ...)
Funciona, mas frágil e enganoso. Se returnPct mudar de semântica, quebra silenciosamente. Melhor passar CostSOL real.

15. monitor.tracked só guarda o mint — sem estado de posição
Para trailing stop / ladder, você precisa em memória: entryMcap, peakMcap, highestReturnPct. Hoje toda decisão de exit bate no DB — latência alta em mercado onde 300ms decide saída.

16. Sem anti-bundle
O criador pode comprar 90% do supply no mesmo bloco do lançamento. Seu RugCheck não vê isso em tempo real. Precisaria comparar preTokenBalances do criador nos primeiros slots pós-launch.

17. dashboard retorna dados mock
go
"tradesByPeriod": []map[string]any{{"period": now.Format("2006-01-02"), "total": len(trades), "positive": 0, "negative": 0}},
"cumulativeResult": []map[string]any{{"timestamp": now, "value": realizedPnl}},
"analyzedTokens": detected,  // = detected, sem análise real
O painel mostra números fictícios. Não é bug crítico, mas mascara que métricas reais não existem. Você precisa de:

Win rate real

Avg hold time

Avg PnL/win, PnL/loss

Sharpe

Fees paid vs. gross PnL

18. Sem "dry-run" do exit
CloseLivePosition chama db.PositionCost(mint) que precisa existir. Se a posição veio de compra que virou unknown (RPC timeout após submit), não há linha em positions — mas o token pode estar na carteira. Bot não vende → bag holding eterno.

Sugestão: ao reconciliar como confirmado, sempre OpenPosition com custo deduzido do Execution() delta. Já faz isso em confirm, mas o caminho de reconciliação pós-restart não chama OpenPosition — verificar Reconcile.

19. DailyRealizedLossSOL usa Truncate(24*time.Hour)
Truncate(24h) alinha em epoch UTC, não "últimas 24h". Funciona por acidente para UTC, mas now.Truncate(24h) = 00:00 UTC de hoje, então "perda diária" reinicia à meia-noite UTC (o que é comportamento desejado por acaso). Mas se mudar fuso, quebra. Explicitar.

20. pending estado nunca vira confirmed se RPC ficar fora
No confirm, se RPC falha com erro repetidamente, state = "pending" fica atualizando, mas nunca é marcado unknown. Timeout do contexto resolve (vira unknown), mas MaxWaitSeconds=45 é muito — em pump.fun, se não confirmou em 10s, já foi (comprou ou rejeitou).

Reduzir MAX_CONFIRMATION_WAIT_SECONDS para 15–20.

🎯 Recomendações priorizadas para lucro
P0 — Sem isso não há lucro
Corrigir economia: TRADE_USD ≥ 25, MAX_PRIORITY_FEE ≤ 0.001, TAKE_PROFIT 30–50%, STOP_LOSS 15–25% (live e sim).

Adicionar trailing stop (12–20% do pico) — a maior fonte de edge em pump.fun.

Adicionar ladder de saída (50% em +30%, 50% em +60%).

Corrigir vazamento de reserved — defer e.release() em todas as saídas de confirm.

Reduzir janela de confirmação para 15s + reconhecer unknown como fail-fast.

P1 — Multiplica edge
Esperar first-dip (2–8s de delay + monitorar marketCapSol caindo 5–20% antes de entrar).

Checagem de dev holdings (rugcheck /report completo + parse de preTokenBalances no primeiro bloco).

Priority fee dinâmico (75º percentil dos últimos 150 slots).

MAX_SUBMISSION_ATTEMPTS = 3, skipPreflight: true.

Autenticar WS com token HMAC na query string.

P2 — Robustez
Limpar m.seen (TLL 30min) e m.tracked em exit.

Estado de posição em memória (entry mcap, peak, mcap atual) para exit <50ms.

Reconciliar pós-restart chamando OpenPosition quando confirmado.

Token de sessão com TTL (1h).

Remover cors morto.

Verificar escala de score_normalised no RugCheck.

P3 — Observabilidade
Métricas reais (win rate, avg PnL/win, fees paid).

Log estruturado de reason de rejeição com distribuição (top 5 razões por hora).

Alerta no Telegram/Discord em risk_alert.

📈 Resumo executivo
Arquitetura: 8/10 — segurança e reconciliação acima da média.
Estratégia: 2/10 — quase inexistente além de "RugCheck passa → compra".
Exit: 3/10 — sem trailing/ladder, TP fixo de 70% raramente acontece.
Economia (defaults): 1/10 — matematicamente inviável lucrar.
Robustez operacional: 5/10 — vaza reserva, vaza memória, sessão eterna.
